2. 背景・目的
- 背景：旅行を考える際、どこに行けばいいかわからない。観光地の場所がわからないため、旅行の計画・経路が立てづらい。
- 解決したい課題：サイトで調べて情報を収集すると、テキストでの情報で視覚的にわかりづらかったり、現地の写真が少なくイメージが持ちづらい。
- このプロダクト / 機能の目的（Why）：マップ上で人気スポットや観光地にピンを指して視覚的にわかりやすくする。行きたい場所を挙げると自動でおすすめの経路を作ってくれる。また、観光地の情報についてはユーザーがユーザーのために投稿し共有する仕組みづくりを構築する。ユーザーの投稿は、現地の映え写真と共にピンが指されてマップ上に表示される。ピンが多い場所は人気スポットであると視覚的にもわかりやすい。観光名所とされていないような場所でも、「隠れた名所」の視覚化として機能する可能性もある。
- 成功イメージ（ユーザーがどうなっていたいか など）：旅行先での観光地や人気スポットが瞬時にわかり、どう回ればいいかもわかる。県や市、施設ごとの広告という表面的な情報ではなく、実際に観光したことがある人が、より生の情報を届けてくれる。

 ▫ 行きたい場所リスト（お気に入り）の作成

 ▫ ユーザー登録・ログイン

- ペルソナ名：旅行計画者（主に大学生）
- 属性（年齢 / 職業 / スキルレベル など）：21歳、学生
- 行動パターン・利用シーン：まとまった休みに友達と旅行を計画している。旅行を計画したいが、サイトの情報を漁っている人。

5. ユースケース / ユーザーストーリー
- ユーザーストーリー例：
「[ペルソナ] が [状況] のときに、[行動] することで [価値] を得られる」
 ▫ 旅行を計画している大学生が、行き先を決めかねているときに、マップ上の投稿が多いエリアを見ることで、人気の旅行先を直感的に見つけられる。
 ▫ 旅行先が決まった大学生が、現地で何を見るか調べているときに、ピンをタップして実際の写真や投稿を見ることで、行く前に現地の雰囲気をイメージできる。
 ▫ 行きたい場所が複数ある大学生が、回る順番に悩んでいるときに、行きたい場所リストから経路を自動作成することで、計画疲れせずに無理のない旅程を立てられる。
 ▫ 旅行中の大学生が、良かった場所をその場で共有したいときに、写真付きで投稿することで、他の旅行者の役に立てる。
- 代表的なユースケース一覧：
 ▫ UC1：旅行先を探すとき、マップを開いて投稿が集まっているエリアから人気スポットを見つける。
 ▫ UC2：気になったピンを選択し、スポットの写真・コメント・投稿数を確認する。
 ▫ UC3：気になったスポットを「行きたい場所リスト」に追加する。
 ▫ UC4：行きたい場所リストから出発地・移動手段・旅行のペースなどを選び、おすすめの回り方（経路）を自動作成する。
 ▫ UC5：旅行中に、その場で写真とコメントを投稿してマップにピンを立てる。
6. 機能要件
- F-1：マップ表示・ピン表示
 ▫ 概要：地図上に観光地とユーザー投稿のピンを表示し、人気スポットを視覚的に把握できるようにする。
 ▫ 詳細仕様：
  ・表示中の地図範囲内にある投稿をピンとして表示する。
  ・ピンを選択するとサムネイル写真とスポット名をポップアップで表示し、詳細画面（F-3）へ遷移できる。
  ・初期表示は現在地（位置情報許可時）または日本全体。
  ・ピンの集まりの表示方法（提案中：ADR-0009）：ズームレベルに応じて表示を切り替える。
   - 広域（都道府県〜日本全体）：ヒートマップ。投稿が多いエリアほど暖色で明るく光る。
   - 中域（市区町村）：写真の束（スタック）。そのエリアで一番人気の写真を表に出し、投稿が多いほど写真が重なって厚く・大きく見える。件数は小さなバッジで補足する。
   - 詳細（スポット単位）：1スポット＝1枚の写真ピン。投稿数に応じて枠の色を3段階で変える。
 ▫ 入力 / 出力：
  ・入力：地図の表示範囲（緯度経度の矩形）、ズームレベル
  ・出力：範囲内のピン一覧（スポットID、緯度経度、代表サムネイルURL、投稿数）
 ▫ 例外・エラー時の挙動：
  ・地図の読み込み失敗時は「地図を読み込めませんでした」と表示し、再読み込みボタンを出す。
  ・位置情報が拒否された場合は日本全体を初期表示する。
  ・範囲内に投稿がない場合は「このエリアにはまだ投稿がありません」と表示し、投稿を促す。
  ・写真の読み込みに失敗したピンは、カテゴリのアイコンで代わりに表示する。

- F-2：スポット投稿
 ▫ 概要：ユーザーが訪れた場所を写真・コメント付きで投稿し、マップ上にピンを立てる。
 ▫ 詳細仕様：
  ・ログインユーザーのみ投稿可能。
  ・位置は「スポット名検索」「GPS（現在地）」のいずれかで指定する（ADR-0006）。地図上のタップによる指定や写真のEXIF位置情報からの自動設定は行わない。
   - 理由：地図上でのタップはユーザーの負担が大きく、写真のEXIFよりGPSの方が位置が正確なため。また、旅行中にその場で投稿してもらうことを促したいため。
  ・GPSで指定した場合は、近くの既存スポット候補を表示し、選ぶだけで投稿できるようにする。
  ・写真は1投稿につき1〜4枚、1枚あたり最大10MB（JPEG / PNG / HEIC）。アップロード時にリサイズし、EXIF情報（位置情報・撮影機器情報など）はすべて除去する。
  ・コメント（最大150文字）（ADR-0007）、カテゴリ（自然・グルメ・歴史・映え・その他など）を設定できる。
   - 理由：500文字では長すぎて、読む側の負担が大きいため。
  ・滞在時間（任意）：〜30分 / 〜1時間 / 〜2時間 / 半日以上 から選択できる（提案中：ADR-0010。F-5の滞在時間の推定に使う）。
  ・投稿日時は自動で記録する（F-5のおすすめ時間帯の推定に使う）。
  ・既存スポットの近く（例：半径50m以内）に投稿した場合は、同一スポットへの投稿としてまとめる。
  ・自分の投稿は編集・削除できる。
 ▫ 入力 / 出力：
  ・入力：写真、位置（スポット名検索の結果またはGPSの緯度経度）、コメント、カテゴリ、滞在時間（任意）
  ・出力：投稿ID、マップへのピン反映
 ▫ 例外・エラー時の挙動：
  ・未ログイン時はログイン画面へ誘導する。
  ・位置情報の利用が拒否された、またはGPSで位置が取得できない場合は「スポット名検索」で指定するよう案内する。
  ・GPSの精度が低い場合（例：誤差100m以上）は、近くのスポット候補から選んでもらう。
  ・写真の形式・サイズ違反、必須項目未入力、コメントの150文字超過時は該当項目にエラーメッセージを表示し、投稿しない。入力中は残り文字数を表示する。
  ・アップロード失敗時は入力内容を保持したまま再試行できるようにする。

- F-3：スポット詳細・検索
 ▫ 概要：スポットの写真・投稿を一覧で閲覧し、エリアやカテゴリで探せるようにする。
 ▫ 詳細仕様：
  ・詳細画面ではスポット名、住所、投稿写真ギャラリー、コメント一覧、投稿数、いいね数、平均的な滞在時間、投稿が多い時間帯を表示する。
  ・投稿に「いいね」できる（人気度の指標に利用）。
  ・不適切な投稿を通報できる。
  ・検索：キーワード（スポット名・地名）、都道府県・市区町村、カテゴリで絞り込み。並び順は人気順（投稿数・いいね数）／新着順。
 ▫ 入力 / 出力：
  ・入力：スポットID、または検索条件（キーワード、エリア、カテゴリ、並び順）
  ・出力：スポット詳細情報、または検索結果一覧（地図とリストの両方に反映）
 ▫ 例外・エラー時の挙動：
  ・削除済み・存在しないスポットの場合は「このスポットは見つかりませんでした」と表示する。
  ・検索結果0件の場合は条件の変更を促すメッセージを表示する。

- F-4：行きたい場所リスト
 ▫ 概要：気になったスポットを保存し、旅行計画の候補としてまとめる。
 ▫ 詳細仕様：
  ・ログインユーザーは複数のリスト（例：「京都旅行」）を作成できる。
  ・スポット詳細画面やマップのポップアップから、ワンタップでリストに追加・削除できる。
  ・リスト内のスポットを地図上に一括表示できる。
  ・リスト内のスポットに「必ず行きたい」の印を付けられる（F-5で優先する）。
  ・共有用URLを発行し、旅行に行く友達と閲覧できる（閲覧のみ）。
 ▫ 入力 / 出力：
  ・入力：リスト名、スポットID、「必ず行きたい」の印
  ・出力：リスト内スポット一覧、共有URL
 ▫ 例外・エラー時の挙動：
  ・未ログイン時はログイン画面へ誘導する。
  ・同じスポットの重複追加は無視し「追加済みです」と表示する。
  ・リスト内のスポットが削除された場合は「このスポットは削除されました」と表示する。

- F-5：おすすめ経路の自動作成
 ▫ 概要：行きたい場所リストから、移動距離だけでなく各スポットの滞在時間やおすすめの時間帯も考慮して、無理なく回れる順番と経路を自動で作成する。
 ▫ 詳細仕様（提案中：ADR-0010）：
  ・条件入力はチャットではなく、選択式の項目で行う（MVP）。
   - 出発地（現在地・駅名・ホテルなど）、到着地（任意）
   - 開始時刻・終了時刻（例：9:00〜18:00）
   - 移動手段（徒歩・車・公共交通）
   - 旅行のペース：ゆったり / ふつう / たくさん回りたい（滞在時間を ×1.3 / ×1.0 / ×0.8 で調整）
   - 重視するもの（複数選択）：写真映え / グルメ / 歴史・文化 / 自然
   - 昼食休憩を入れるか（入れる場合は11:30〜13:30の間に60分確保）
  ・各スポットの滞在時間は次の優先順で決める。
   1. 投稿で集まった滞在時間の中央値（投稿が3件以上ある場合）
   2. カテゴリごとの標準値（例：神社・寺 30分、美術館 90分、テーマパーク 半日）
  ・各スポットのおすすめ時間帯は、投稿日時の分布から推定する（例：夕方に投稿が集中するスポット＝夕日スポット）。営業時間がわかる場合は営業時間外に訪問しないようにする。
  ・訪問順は「移動時間＋滞在時間」が終了時刻までに収まり、おすすめ時間帯に近く訪問できる順を算出する。8か所以下は全通りを計算し、それ以上は近い順に並べてから入れ替えて改善する方法（2-opt）で求める。
  ・時間内に回りきれない場合は、「必ず行きたい」の印がないスポットから外し、外したスポットを「時間が足りず入らなかった場所」として表示する。
  ・算出した経路を地図上に線で描画し、タイムライン形式（到着時刻・滞在時間・移動時間）で表示する。
  ・ユーザーが訪問順や滞在時間を手動で変更した場合は時刻を再計算する。
  ・作成した経路はリストに保存できる。
  ・AIチャットによる条件入力はMVPでは行わない。将来、チャットの内容から上記の項目を自動入力する補助機能として追加を検討する。
 ▫ 入力 / 出力：
  ・入力：スポットID群、出発地、（任意）到着地、開始・終了時刻、移動手段、旅行のペース、重視するもの、昼食休憩の有無
  ・出力：訪問順、各スポットの到着時刻・滞在時間、区間ごとの経路・移動時間、合計所要時間、入らなかったスポット
 ▫ 例外・エラー時の挙動：
  ・経路が見つからない区間（離島など）は「この区間の経路が見つかりませんでした」と表示し、その区間を除いて提案する。
  ・スポット数が上限（10か所程度）を超える場合は上限内に絞るよう促す。
  ・「必ず行きたい」スポットだけでも時間内に収まらない場合は、終了時刻を延ばすか、スポットを減らすよう案内する。
  ・経路APIのエラー時、または無料枠の上限に達して停止している場合は「現在、経路作成を利用できません」と表示する。
7. 非機能要件
- パフォーマンス（レスポンス目標、同時接続数 など）：
 ▫ マップの初期表示 3秒以内、地図移動時のピン再描画 1秒以内を目標とする。
 ▫ 経路作成は10か所で5秒以内。
 ▫ 画像はリサイズ・サムネイル生成し、CDN経由で配信する。
 ▫ MVP段階では同時接続100ユーザー程度を想定する。
- セキュリティ（認証 / 権限 / ログ / 個人情報 など）：
 ▫ メールアドレス＋パスワード、またはGoogleアカウントによるログイン（認証基盤はSupabase Auth / Firebase Authentication等の既存サービスを利用）。
 ▫ 投稿の編集・削除は投稿者本人のみ可能（DBの行レベルの権限制御で担保）。
 ▫ 写真のEXIF情報はすべて除去する。GPSで取得した位置はスポットの位置としてのみ使い、ユーザーの現在地そのものは保存しない。
 ▫ 通信はすべてHTTPS。APIキーはサーバー側で管理し、フロントに公開するキーはドメイン制限をかける。
 ▫ 不適切な投稿は通報機能と管理者による非表示で対応する。利用規約・プライバシーポリシーを用意する。
- 可用性（稼働時間、障害対応方針など）：
 ▫ 学生プロジェクトのためSLAは設けない。マネージドサービス（Vercel、Supabase等）の無料プランを利用する。
 ▫ 障害時は気づいたメンバーがチャットで共有し、ロールバック（直前のデプロイに戻す）で対応する。
 ▫ DBのバックアップ（提案中：ADR-0011）：
  ・GitHub Actionsで毎日深夜（例：午前3時）にDBのダンプ（pg_dump / supabase db dump）を取得する。
  ・ダンプは暗号化して、非公開のGitHubリポジトリのArtifact、またはCloudflare R2（無料枠10GB）に保存する。保存期間は30日。
  ・写真（ストレージ）はDBのダンプに含まれないため、週1回、別途コピーする。
  ・月1回、ローカル環境に復元できるか確認する。
- スケーラビリティ：
 ▫ サーバーレス構成とし、アクセス増加時は自動スケールに任せる。
 ▫ ピン数の増加に備え、位置情報にインデックス（PostGIS等）を張り、表示範囲での絞り込み・クラスタリングをサーバー側で行う。
 ▫ 外部APIは無料枠の範囲内で利用する。結果をキャッシュして呼び出し回数を抑える（例：同じ区間の移動時間はDBに保存して再利用する）。
- 運用・監視（メトリクス、アラート条件 など）：
 ▫ メトリクス：DAU、投稿数、経路作成回数、エラー率、APIレスポンス時間、外部API利用量。
 ▫ アラート：エラー率5%超過時に通知。
 ▫ 外部API利用量が無料枠の80%に達したら、そのAPIを使う機能を自動で停止する（ADR-0008）。停止中はユーザーに「現在利用できません」と表示し、翌月の枠リセット時に再開する。外部サービス側でも1日あたりの利用上限（クォータ）を設定し、二重に防ぐ。
 ▫ ツール：Vercel Analytics、Sentry等のエラー監視（いずれも無料プラン）を利用する。
8. 画面・UI/UX
- 主要画面一覧：
 ▫ トップ（マップ）画面：ピン表示（ヒートマップ／写真の束／写真ピン）、検索バー、カテゴリ絞り込み、投稿ボタン
 ▫ スポット詳細画面：写真ギャラリー、コメント一覧、平均滞在時間、投稿が多い時間帯、いいね、リスト追加、通報
 ▫ 投稿画面：写真選択、位置指定（スポット名検索 / GPS）、コメント・カテゴリ・滞在時間入力
 ▫ 検索結果画面：地図＋リスト表示
 ▫ 行きたい場所リスト画面：リスト一覧・リスト詳細・共有
 ▫ 経路作成画面：条件入力（出発地・時刻・移動手段・ペース・重視するもの）、タイムラインと地図での経路表示
 ▫ ログイン / 新規登録画面
 ▫ マイページ：自分の投稿一覧、プロフィール編集
- 画面遷移図（別資料でも可）：
 ▫ トップ（マップ） → ピン選択 → スポット詳細 → 行きたい場所リストに追加
 ▫ トップ（マップ） → 検索 → 検索結果 → スポット詳細
 ▫ トップ（マップ） → 投稿ボタン →（未ログインならログイン）→ 投稿画面 → 投稿完了でマップに戻る
 ▫ 行きたい場所リスト → 経路作成（条件入力） → 経路表示 → 保存
 ▫ ヘッダー / ボトムナビから：マップ・リスト・投稿・マイページへ移動
 ▫ 詳細な遷移図は別資料（Figma）で作成予定
- ワイヤーフレーム / モック（Figmaリンクなど）：作成予定（Figmaリンクは作成後に追記）
- UX上の重要なポイント（やってほしいこと / やってほしくないこと）：
 ▫ やってほしいこと：
  ・地図がメインの画面構成にし、写真で直感的に「行きたい」と思えるようにする。
  ・投稿の多さを数字ではなく、写真の重なりや色の明るさで直感的に伝える。
  ・スマホのブラウザで片手操作しやすいレイアウト（モバイルファースト）にする。
  ・投稿は数タップで完了できるようにし、GPSで近くのスポット候補を出して選ぶだけで済むようにする。
  ・ログインなしでもマップ閲覧・スポット閲覧はできるようにする。
 ▫ やってほしくないこと：
  ・ピンを大量に表示して地図が見えなくなること（ズームに応じた表示切り替えで対応）。
  ・閲覧の最初にログインを強制すること。
9. データ要件
- 主要エンティティと項目　：
 ▫ User：ユーザーID、表示名、メールアドレス、アイコン画像、作成日時
 ▫ Spot：スポットID、スポット名、緯度、経度、住所、都道府県、市区町村、カテゴリ、投稿数、代表写真ID、滞在時間の中央値、営業時間（取得できる場合）、作成日時
 ▫ Post：投稿ID、ユーザーID、スポットID、コメント（最大150文字）、カテゴリ、滞在時間（任意）、いいね数、公開状態、作成日時、更新日時
 ▫ PostImage：画像ID、投稿ID、画像URL、サムネイルURL、表示順
 ▫ Like：ユーザーID、投稿ID、作成日時
 ▫ WishList：リストID、ユーザーID、リスト名、共有用トークン、作成日時
 ▫ WishListItem：リストID、スポットID、必ず行きたいフラグ、追加日時
 ▫ Route：経路ID、リストID、出発地、開始・終了時刻、移動手段、ペース、重視するもの、訪問順（スポットIDと到着時刻・滞在時間の配列）、合計所要時間、作成日時
 ▫ TravelTimeCache：出発スポットID、到着スポットID、移動手段、移動時間、取得日時（API呼び出し削減用）
 ▫ ApiUsage：API種別、年月、呼び出し回数、停止フラグ（無料枠管理用）
 ▫ Report：通報ID、投稿ID、通報ユーザーID、理由、対応状況、作成日時
- データフロー（どこから来てどこへ保存されるか）：
 ▫ 投稿：ブラウザ → 画像はストレージ（Supabase Storage等）へアップロード → 投稿情報はDB（PostgreSQL）へ保存 → スポットの投稿数・滞在時間の中央値を更新 → マップ表示時にDBから表示範囲内のスポットを取得
 ▫ 経路：行きたい場所リスト（DB）→ 移動時間はキャッシュ（TravelTimeCache）を優先し、ない区間だけ経路APIへ問い合わせ → サーバーで訪問順を計算 → 結果をブラウザで描画、保存時はDBへ
 ▫ スポット名・住所：スポット名検索・GPSの結果から取得しDBへ保存
 ▫ バックアップ：DB → GitHub Actions（日次ダンプ）→ 暗号化して外部ストレージへ保存（ADR-0011）
- 外部サービス・APIとの連携（仕様・制約）：
 ▫ 方針：すべて無料枠の範囲内で利用する（ADR-0008）。
 ▫ 地図表示：MapLibre GL JS ＋ 無料の地図タイル（OpenFreeMap / MapTiler無料プラン など）（提案中：ADR-0009。ヒートマップと写真ピンを無料で実装しやすいため）。Google Maps JavaScript APIも無料枠内であれば候補とする。
 ▫ 経路・移動時間：徒歩・車はOpenRouteService（無料枠）またはGoogle Routes API（無料枠）。公共交通は無料APIで取得できる範囲が限られるため、開始前に検証する。
 ▫ 場所検索：Google Places API（無料枠）または Nominatim（OpenStreetMap、利用規約の範囲内）
 ▫ 認証・DB・ストレージ：Supabase（または Firebase）の無料プラン
 ▫ 制約：無料枠の上限を超えないよう、利用回数をApiUsageで数え、80%で該当機能を停止する。各サービスの利用規約（データの保存期間・表示義務など）を守る。
- ログ設計（何を、どの粒度で記録するか）：
 ▫ アクセスログ：リクエスト日時、パス、ステータスコード、レスポンス時間（ホスティング標準のログを利用）
 ▫ 操作ログ：投稿作成・編集・削除、いいね、リスト追加、経路作成（ユーザーID、対象ID、日時）
 ▫ エラーログ：例外内容、スタックトレース、発生画面（Sentry等）
 ▫ 外部API利用ログ：API種別、呼び出し回数（無料枠管理用、日次集計）、自動停止・再開の記録
 ▫ バックアップログ：実行日時、成否、ファイルサイズ
 ▫ 個人情報（メールアドレス、正確な現在地）はログに残さない。
10. リリース計画
- マイルストーン（MVP / β版 / 正式リリース など）：
 ▫ MVP：マップ表示（F-1）、スポット投稿（F-2）、スポット詳細（F-3の閲覧部分）、ログイン
 ▫ β版：検索・絞り込み、いいね、行きたい場所リスト（F-4）、経路自動作成（F-5）
 ▫ 正式リリース：通報・管理機能、リストの共有、UI改善、パフォーマンス改善
- ロールアウト戦略（段階的リリース / A/Bテスト など）：
 ▫ 段階的リリース：開発メンバー → 友人・知人（クローズドβ）→ 一般公開
 ▫ 初期は投稿が少なくピンがまばらになるため、公開前にメンバーで代表的な観光地の投稿を用意しておく（初期データ投入）。滞在時間も入力しておき、F-5の推定に使えるようにする。
 ▫ ユーザー数が増えた段階で、ピン表示方法などをA/Bテストで比較する。
11. リスク・課題
- 想定されるリスク：MVPでは考慮しない（正式リリース前に再検討する）。
- 技術的な不確実性：
 ▫ 日本国内の公共交通機関の経路を無料APIでどこまで取得できるか。
 ▫ 訪問順の計算（滞在時間・時間帯を含む巡回の問題）の計算時間と、API呼び出し回数の増加。
 ▫ 投稿が少ないスポットの滞在時間・おすすめ時間帯の推定精度。
 ▫ 大量のピン（写真）表示時の描画パフォーマンス。
 ▫ 近い位置の投稿を「同じスポット」とまとめる判定ロジックの精度。
 ▫ 無料プランの制限（例：Supabase無料プランは一定期間アクセスがないとプロジェクトが一時停止される）。
- ビジネス上の懸念点：
 ▫ 無料枠の範囲で運用するため、利用者が増えると機能停止が起きやすくなる一方で収益源がない。
 ▫ Googleマップ、Instagram、旅行予約サイトなど既存サービスとの差別化。
 ▫ 将来の収益化（広告など）が「広告ではない生の情報」というコンセプトと衝突する可能性。
- リスクに対する対応方針：
 ▫ 経路の不確実性：開発初期にAPIの検証（PoC）を行い、公共交通が難しい場合は徒歩・車から対応する。
 ▫ 推定精度：投稿が少ないうちはカテゴリごとの標準値を使い、投稿が集まるにつれて実データに切り替える。
 ▫ コスト：無料枠の80%で自動停止、移動時間のキャッシュ、オープンソースの地図（OpenStreetMap系）の採用。
