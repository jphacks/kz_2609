# ADR（Architecture Decision Record）

プロダクト：仮　旅行どこいこう
関連資料：PDR_v3.md

## 運用ルール
- 1つの決定につき1つのADRを書く。番号は通し番号（ADR-0001, ADR-0002, ...）で、使い回さない。
- **決定を変えるときは、既存のADRを書き換えずに新しいADRを追加し、古いADRの状態を「書き換え済み」にする。**
 ▫ 古いADRで変更してよいのは「状態」と「書き換え先」の欄だけ。本文は残す（なぜ当時そう決めたかを後から追えるようにするため）。
 ▫ 新しいADRの「書き換え元」に古いADRの番号を書く。
- 状態は次のいずれか。
 ▫ 提案中：案を出した段階。チームの合意はまだ。
 ▫ 承認済み：チームで合意した。
 ▫ 却下：検討したが採用しなかった。
 ▫ 書き換え済み：新しいADRで決定が変更された。
- 提案中のADRの決定内容を変えたい場合も、合意前なら同じADRを修正してよいが、承認済みになった後は新しいADRを追加する。

## ADR-0001：投稿位置の指定方法（地図タップ・スポット名検索・EXIF）
- 状態：書き換え済み
- 日付：2026/10/09
- 書き換え先：ADR-0006

### 背景
投稿にはスポットの位置が必要。旅行後にまとめて投稿するケースも想定していた。

### 決定
位置は「地図上でタップして指定」「スポット名検索」「写真のEXIF位置情報から自動設定」のいずれかで指定する。

### 理由
- 旅行後に自宅から投稿する場合でも、写真のEXIFから位置を自動入力できる。
- 名前のない場所（隠れた名所）でも地図タップで指定できる。

### 影響
- EXIFの位置情報を読み取るため、写真のメタデータの扱いに注意が必要。

- 状態：書き換え済み
- 日付：2026/10/09
- 書き換え先：ADR-0007

### 背景
投稿には写真に加えてコメントを付けられるようにする。

コメントの最大文字数は500文字とする。

### 影響

## ADR-0003：外部API利用料のアラート（月予算80%で通知）
- 状態：書き換え済み
- 日付：2026/10/09
- 書き換え先：ADR-0008

### 背景
地図・経路APIは従量課金のため、使いすぎを防ぐ必要がある。

### 決定
外部APIの利用料が月予算の80%に達したらメンバーに通知する。

### 理由
- 通知を受けたメンバーが状況を見て対応を判断できるため。

### 影響
- 通知に気づかない、対応が遅れると、予算を超えて課金される可能性がある。

## ADR-0004：ピンの集まりの表示方法（数字のクラスタ）
- 状態：書き換え済み
- 日付：2026/10/09
- 書き換え先：ADR-0009

### 背景
投稿が増えるとピンが重なり、地図が見えなくなる。

### 決定
ズームアウト時は近接するピンをクラスタリングし、件数を数字で表示する。件数が多いほど色・サイズを強調する。

### 理由
- 地図ライブラリの標準的な方法で、実装が簡単なため。

### 影響
- 数字だけでは「たくさん投稿がある」ことが直感的に伝わりにくい。

## ADR-0005：経路作成の最適化基準（移動時間のみ）
- 状態：書き換え済み
- 日付：2026/10/09
- 書き換え先：ADR-0010

### 背景
行きたい場所リストから、おすすめの回り方を自動で作成したい。

### 決定
選択したスポットについて、総移動時間が最短になる訪問順を算出する。

### 理由
- 経路APIのウェイポイント最適化機能をそのまま使え、実装が簡単なため。

### 影響
- 滞在時間や営業時間、おすすめの時間帯を考慮しないため、「移動は短いが時間内に回りきれない」「夕日スポットに昼に着く」といった経路になる可能性がある。

## ADR-0006：投稿位置の指定方法（スポット名検索・GPS）
- 状態：承認済み
- 日付：2026/10/10
- 書き換え元：ADR-0001

### 背景
ADR-0001では地図タップ・スポット名検索・EXIFの3つの方法を用意していたが、地図タップはユーザーの負担が大きく、EXIFは位置の精度に不安がある。また、旅行中にその場で投稿してもらうことを促したい。

### 決定
位置は「スポット名検索」「GPS（現在地）」のいずれかで指定する。地図タップとEXIFからの自動設定は行わない。

### 理由
- 地図上でのタップはユーザーの負担が大きい。
- 写真のEXIFよりもGPSの方が位置が正確。
- その場で投稿してもらいたい（GPSを使うことで、その場での投稿が自然な流れになる）。

### 影響
- GPSで指定したときは近くの既存スポット候補を出し、選ぶだけで投稿できるようにする。
- 位置情報が拒否された・取得できない場合はスポット名検索に案内する。
- 写真のEXIF情報は使わないため、すべて除去できる（プライバシー面でも安全になる）。
- 旅行後に投稿する場合や名前のない場所は、スポット名検索で見つからないと投稿しづらい。投稿の状況を見て、必要なら再検討する。
- 投稿日時が実際の訪問時刻に近くなるため、ADR-0010のおすすめ時間帯の推定に使える。

## ADR-0007：投稿コメントの最大文字数（150文字）
- 状態：承認済み
- 日付：2026/10/10
- 書き換え元：ADR-0002

### 背景
ADR-0002では500文字としていたが、長すぎて読む側の負担が大きい。

### 決定
コメントの最大文字数は150文字とする。

### 理由
- 500文字だと多すぎて、読む側の負担が大きくなるため。写真がメインで、コメントは補足という位置づけにする。

### 影響
- 入力中に残り文字数を表示する。150文字を超えた場合は投稿できない。
- DBのコメント欄にも150文字の制限をかける。

## ADR-0008：外部APIは無料枠内で運用し、80%で自動停止
- 状態：承認済み
- 日付：2026/10/10
- 書き換え元：ADR-0003

### 背景
ADR-0003では月予算の80%で通知するとしていたが、通知だけでは課金を確実には防げない。学生プロジェクトであり、基本的に無料で使える範囲で運用したい。

### 決定
- 外部API（地図・経路・場所検索など）は無料枠の範囲内で利用する。
- 利用量が無料枠の80%に達したら、そのAPIを使う機能を自動で停止する。翌月の枠リセット時に再開する。

### 理由
- 通知ではなく停止にすることで、意図しない課金を確実に防げる。

### 影響
- API呼び出し回数をアプリ側で数える（ApiUsageテーブル）。外部サービス側でも1日あたりの利用上限（クォータ）を設定し、二重に防ぐ。
- 停止中は該当機能に「現在利用できません」と表示する。停止が起きにくいよう、移動時間などの結果をキャッシュして呼び出し回数を減らす。
- 無料枠が大きい・無料で使えるサービス（MapLibre＋OpenStreetMap系の地図タイル、OpenRouteServiceなど）を優先して選ぶ。
- 利用者が増えると停止が起きやすくなる。その場合は有料化や別サービスへの切り替えを新しいADRで検討する。

## ADR-0009：ピンの集まりをズームに応じてヒートマップ・写真の束で表示
- 状態：承認済み（2026/10/12。方向性として承認し、実装して気になる点は随時見直す）
- 日付：2026/10/10
- 書き換え元：ADR-0004

### 背景
ADR-0004の「数字のクラスタ」では、たくさん投稿があることが視覚的にわかりにくい。このアプリは「写真で直感的に行きたいと思える」ことが大事なので、投稿の多さも写真や色で伝えたい。

### 検討した案

| 案 | 内容 | 良い点 | 気になる点 |
| --- | --- | --- | --- |
| A. 数字のクラスタ（現状） | 円の中に件数 | 実装が簡単 | 多さが直感的に伝わらない、写真が見えない |
| B. ヒートマップ | 投稿が多いエリアが暖色で光る | 広域で「どこが盛り上がっているか」が一目でわかる | ズームインすると個々のスポットがわからない |
| C. 写真の束（スタック） | 一番人気の写真を表に出し、投稿が多いほど写真が重なって厚く・大きく見える | 写真が見えて「行きたい」につながる。多さも厚みでわかる | 写真の読み込みが多く、表示が重くなりやすい |
| D. 人気度の段階表示 | 投稿数で枠の色やアイコン（例：炎マーク）を3段階に変える | ひと目で人気度がわかる | 単体では写真の魅力は伝わらない |

### 決定（案）
ズームレベルに応じて B → C → D を切り替える。
- 広域（都道府県〜日本全体）：B ヒートマップ。
- 中域（市区町村）：C 写真の束。サイズは投稿数に応じて段階的に大きくする（数件と数百件で極端に差が出ないよう、対数で調整）。件数は小さなバッジで補足する。
- 詳細（スポット単位）：1スポット＝1枚の写真ピン＋D 人気度の枠の色。

### 理由
- 広域では「どこが人気か」、近づくと「どんな場所か」と、ユーザーが知りたいことが段階的に変わるため。
- 数字を主役にせず、色と写真の重なりで多さを伝えられる。

### 影響
- 地図ライブラリは、ヒートマップと写真の独自ピンを無料で実装しやすい MapLibre GL JS を候補とする（地図タイルは OpenFreeMap / MapTiler無料プラン等）。Google MapsのヒートマップレイヤーはGoogle側で非推奨になっているため。
- クラスタの計算は Supercluster などのライブラリ、またはサーバー側（PostGIS）で行う。
- 写真ピンには小さなサムネイル（例：64px）を使い、表示範囲内のものだけを読み込む。
- 決定前に、簡単なモックで「わかりやすさ」と「表示の重さ」をメンバーで確認する。

## ADR-0010：滞在時間・時間帯を考慮した経路作成と、3つの作り方（おまかせ・選択式・AIと相談）
- 状態：承認済み（2026/10/12。提案中の段階で、作り方を「選択式のみ」から「3つから選ぶ」に修正したうえで承認）
- 日付：2026/10/12（提案 2026/10/10）
- 書き換え元：ADR-0005

### 背景
ADR-0005では移動時間が最短になる順を出すだけだったが、実際の旅行では「各スポットにどれくらい滞在するか」「いつ行くのが良いか（夕日・朝の空いている時間など）」「営業時間」も重要。
また、ユーザーが何を重視するか（ゆったり回りたい・たくさん回りたい など）を、AIのチャットで聞くか、選択式の項目で聞くかで迷っていた。
経路やプランの計画は旅行計画で一番大変な作業であり、本サービスの強みとして自動化したい。一方、ユーザーによって「手早く決めたい」「細かい希望を伝えたい」「とにかく負担の少ない回り方がいい」と求めるものが違う。

### 検討した案（条件の入力方法）

| 案 | 内容 | 良い点 | 気になる点 |
| --- | --- | --- | --- |
| A. 選択式の項目 | ペース・重視するもの・時刻などをボタンで選ぶ | 無料で実装できる。数タップで終わる。結果が安定し、テストしやすい | 細かい希望は伝えにくい |
| B. AIチャット | 「夕日が見たい、のんびり回りたい」などを会話で伝える | 自由に希望を伝えられる | LLMのAPIは無料枠が小さく、ADR-0008の方針と合いにくい。回答が毎回ぶれる。入力に時間がかかる |
| C. A＋B（AIは補助） | 基本は項目選択。AIは自由入力の文章から項目を自動で埋めるだけ | Aの安定性を保ちつつ、自由な希望も受け付けられる | 実装が2段階になる |
| D. 3つから選ぶ | 「おまかせ」「選択式（A）」「AIと相談（B。AIは条件の読み取りだけ）」をユーザーが選ぶ | 手早さ・細かさ・負担の少なさのどれを求めるユーザーにも合う | 実装量が最も多い。AIは無料枠の管理が必要 |

### 決定
**D とする。** 経路の作り方を次の3つから選べるようにする。
1. おまかせ：追加の入力なし。移動時間・滞在時間・おすすめの時間帯から、移動の負担が最も少ない案を作る。
2. 重視するものを選ぶ（A）：ペース・重視するもの・優先することを選択式で選ぶ。
3. AIと相談（B）：チャットで自由に希望を伝える。**AIは会話を条件（ペース・重視するもの・時刻の指定・順番の希望など）に変換するだけで、経路そのものは作らない。** 変換した条件はユーザーが確認・修正してから作成する。

- 3つとも、条件を共通の形にそろえた後は同じ計算ロジックで経路を作る。
- 1回の作成で、特徴の違う経路案を最大3案出し、ユーザーが比べて選べるようにする。
- 滞在時間の求め方：
 1. 投稿時に任意で選んでもらう滞在時間（〜30分 / 〜1時間 / 〜2時間 / 半日以上）の中央値（3件以上ある場合）
 2. それ以外はカテゴリごとの標準値
 3. 「重視するもの」に当てはまるカテゴリのスポットは滞在時間を少し長めにする
- おすすめ時間帯の求め方：投稿日時の分布から推定する（ADR-0006でその場投稿になるため、投稿時刻≒訪問時刻とみなせる）。営業時間は、取り込めるようになった段階で考慮する（要件定義書 16章）。
- 訪問順の計算の詳細（点数の付け方・複数案の出し方）は、要件定義書 15章で検討する。

### 理由
- 計算ロジックを自前で持つことで、AIを使う場合でも結果が安定し、ユーザーへの説明（なぜこの順番か）もしやすい。
- AIの役割を「条件の読み取り」に限定することで、呼び出し回数とデータ量を小さく抑え、無料枠内で運用しやすくなる（ADR-0008）。
- 「その場投稿」で集まる滞在時間と投稿時刻が、そのまま経路作成の精度向上につながり、投稿が増えるほど便利になる。

### 影響
- 投稿フォームに「滞在時間（任意）」を追加する（PDR F-2）。
- Spotに滞在時間の中央値、WishListItemに「必ず行きたい」フラグを追加する。
- AI（Gemini API など）を外部サービスとして追加し、無料枠の80%で「AIと相談」だけを停止する。AIに送る情報と会話の保存方法を決める（要件定義書 15章）。
- 投稿が少ないうちは標準値頼みになるため、初期データ投入時に滞在時間も入力しておく。
- 経路はタイムライン形式（到着時刻・滞在時間・移動時間）で表示し、手動で順番や滞在時間を変えたら再計算する。
- 実装前に、実際の旅行プラン（例：京都で5〜8か所）で試し、出てくる経路が自然かをメンバーで確認する。

## ADR-0011：DBの日次バックアップ方法
- 状態：承認済み（2026/10/12）
- 補足：リポジトリは JPHACKS 指定のチームリポジトリ（公開）に置くため、保存先は Cloudflare R2 とし、GitHub の Artifact には保存しない（公開リポジトリの Artifact は他人もダウンロードできるため）。
- 日付：2026/10/10
- 書き換え元：—

### 背景
投稿データはユーザーが作った大切なデータで、消えると取り戻せない。一方、無料枠内で運用する方針（ADR-0008）であり、Supabaseの無料プランには自動の日次バックアップが付いていない（有料プランのみ）。

### 検討した案

| 案 | 内容 | 費用 | 良い点 | 気になる点 |
| --- | --- | --- | --- | --- |
| A. Supabase有料プランの自動バックアップ | 有料プランに含まれる日次バックアップを使う | 有料 | 設定不要 | 無料方針に合わない |
| B. GitHub Actions ＋ pg_dump | 毎日決まった時刻にDBのダンプを取得し、外部に保存する | 無料（無料枠内） | 無料。手順がコードで残る。復元も pg_dump の標準手順で行える | 自分たちで設定・確認する必要がある |
| C. 手動でダンプ | メンバーが定期的に手動で取得 | 無料 | 簡単 | 忘れる・属人化する |

### 決定（案）
B（GitHub Actions ＋ pg_dump）とする。
- GitHub Actionsのスケジュール実行（cron）で毎日深夜（例：日本時間 午前3時）に実行する。
- `supabase db dump`（または `pg_dump`）でDBのダンプを取得する。DBの接続情報はGitHubのSecretsに保存し、コードに書かない。
- ダンプファイルはgzipで圧縮し、暗号化（例：gpg）してから保存する。
- 保存先は次のいずれか。
 ▫ 非公開のGitHubリポジトリのArtifact（保存期間30日を設定）
 ▫ Cloudflare R2（無料枠10GB、30日より古いファイルは自動削除）
- 写真（ストレージ）はDBのダンプに含まれないため、週1回、別途コピーする（例：rclone で R2 へ同期）。
- 失敗したらGitHubからメンバーにメール通知が届くようにする。
- 月1回、ダンプをローカル環境（Docker等）に復元できるか確認する。

### 理由
- 無料で毎日自動的にバックアップが取れる。
- 設定がリポジトリにコードとして残るため、誰が見ても仕組みがわかる。

### 影響
- バックアップには個人情報（メールアドレス等）が含まれるため、必ず暗号化し、公開リポジトリには保存しない（公開リポジトリのArtifactは他人がダウンロードできるため）。
- 暗号化の鍵は、メンバーのうち管理担当者だけが持つ。鍵を失うと復元できないため、鍵の保管方法を決めておく。
- GitHub Actionsの無料枠（非公開リポジトリは月2,000分）の範囲で十分に収まる見込み。
- Supabase無料プランは一定期間アクセスがないとプロジェクトが一時停止されるため、停止中はバックアップが失敗する。失敗通知で気づけるようにする。
- 利用者が増え、有料プランに移行した場合は、A に切り替えるかを新しいADRで検討する。

## ADR-0012：MVPでは想定リスクへの対応を考慮しない
- 状態：承認済み
- 日付：2026/10/10
- 書き換え元：—

### 背景
PDRでは、投稿不足・不適切投稿・プライバシー・著作権などの想定リスクと、その対応方針を挙げていた。MVPではまず基本機能を形にすることを優先したい。

### 決定
MVPでは想定されるリスクへの対応は考慮しない。正式リリース前に改めて検討する。

### 理由
- MVPの目的は、主要機能（マップ表示・投稿・閲覧）が成り立つかを確認すること。リスク対応まで含めると開発範囲が広がりすぎるため。

### 影響
- PDRの「想定されるリスク」は「MVPでは考慮しない」とし、関連する対応方針を外した。技術的な不確実性への対応（APIの検証など）は引き続き行う。
- 正式リリース前に、リスクと対応方針を新しいADRとして追加する。

## ADR-0014：公共交通の経路に Google Routes API を使い、計画をサイト内で完結させる
- 状態：書き換え済み
- 日付：2026/10/12
- 書き換え元：—
- 書き換え先：ADR-0016

### 背景
対象ユーザーの大学生は車を持たないことが多く、公共交通での移動時間が経路の精度を大きく左右する。無料で使える経路API（OpenRouteService など）は日本の公共交通に対応していない。
また、経路作成では複数の案を比べて選ぶ必要があり、案ごとに外部の地図アプリを開いて確認するのは負担が大きい。

### 検討した案

| 案 | 内容 | 良い点 | 気になる点 |
| --- | --- | --- | --- |
| A. 徒歩・車のみ＋外部リンク | 公共交通は「Googleマップで開く」リンクで確認してもらう | 無料。実装が簡単 | サイトの外へ移動する手間がかかる。案の比較がしにくい。徒歩の時間だと遠い区間が過大になる |
| B. Google Routes API | 無料枠内で公共交通の移動時間・経路を取得する | サイト内で完結し、案を比べやすい | 無料枠を超えると課金。経由地を指定できず区間ごとに呼ぶ必要がある。出発時刻で結果が変わり、キャッシュが効きにくい |

### 決定

### 理由
- 計画をこのサイトの中で完結させ、外部へ移動する手間をなくすため。
- 経路作成で出てくる複数の案を、公共交通の時間を含めて比べられるようにするため。

### 影響
- 無料枠を課金される単位（SKU・組み合わせの件数）で数え、80%で公共交通での経路作成を停止する（ADR-0008）。
- 日本の公共交通がAPIで取得できるかを、開発の最初に検証する（要件定義書 15章）。
- 公共交通を含む場合は、対象スポットの上限を少なめにする。

## ADR-0015：Supabase の使用量が80%に達したら新規投稿だけを停止する
- 状態：承認済み
- 日付：2026/10/12

### 検討した案

| 案 | 内容 | 良い点 | 気になる点 |
| --- | --- | --- | --- |

## ADR-0016：経路作成では計画に必要な移動時間だけを取得し、当日の道案内は Googleマップに任せる
- 状態：書き換え済み
- 日付：2026/10/21
- 書き換え元：ADR-0014
- 書き換え先：ADR-0019

### 背景
ADR-0014 では、公共交通の移動時間と経路（乗る路線・乗換・経路の形）を Google Routes API で取得し、計画をサイト内で完結させるとしていた。
しかし、経路の詳細まで取得すると、区間ごとの呼び出しが増えて無料枠を早く使い切る、実装量が増える、という問題がある。ハッカソンまで時間がないため、作る範囲を絞りたい。
また、要件定義書 v0.2 の15章 Q8 で、外部の地図アプリへのリンクは「保存した経路プランの各区間に『ナビを開始』だけを置く」（案B）と決めた。

### 検討した案

| 案 | 内容 | 良い点 | 気になる点 |
| --- | --- | --- | --- |
| A. 経路の詳細まで取得する（ADR-0014） | 移動時間に加えて、路線・乗換・経路の形を区間ごとに取得して表示する | サイト内で当日の移動まで確認できる | 区間ごとの呼び出しで無料枠の消費が増える。実装量が多い |
| B. 計画に必要な移動時間だけを取得する | 移動時間の行列（1回の呼び出し）だけを取得して訪問順と時刻を決める。路線・乗換・当日の道案内は Googleマップの URL で開く | 呼び出しが少なく、実装が簡単。Googleマップの案内のほうが当日は正確 | 路線や乗換はサイト内では見られない |

### 決定
**B とする。**
- 経路作成（計画）に使うのは、出発地・スポット・到着地のあいだの**移動時間（と距離）の行列だけ**とする。公共交通は Google Routes API、徒歩・車は OpenRouteService の行列を使う（ADR-0013 のとおり）。
- 公共交通の移動時間は、出発時刻の時間帯で取得した「目安」として表示する。順番や滞在時間を変えたときの再計算では、外部APIを呼び直さない。
- 路線名・乗換・経路の形は取得しない。地図上の経路線は、訪問順にスポットを結ぶ線で表す。
- 当日の道案内は、保存した経路プランの各区間に置く「ナビを開始」から Googleマップの URL（APIキー不要・無料）で開く。スポット詳細など計画中の画面には外部リンクを置かない。

### 理由
- 「どの順で、何時に回るか」を決めるのに必要なのは移動時間だけで、路線や乗換の詳細は当日に必要になる情報のため。
- 外部APIの呼び出しを経路作成1回あたり行列1回に減らし、無料枠内で運用しやすくするため（ADR-0008）。
- 当日の道案内は Googleマップのほうが正確で、自前で作る必要がないため。

### 影響
- 要件定義書の F-3-5（スポット詳細の外部リンク）を削除し、F-5-8・F-5-12 を変更する。
- 経路案の表示は「移動手段と所要時間（目安）」までとし、路線・乗換回数は表示しない。
- 移動時間キャッシュから路線などの詳細（summary）を外す。
- 日本の公共交通の移動時間が Routes API で取得できるかの検証は、引き続き開発の最初に行う（要件定義書 15章）。

## ADR-0017：経路作成の範囲（1日分・リスト内・最大8か所）と計算方法
- 状態：承認済み
- 日付：2026/10/21
- 書き換え元：—（ADR-0010 の補足）

### 背景
ADR-0010 では、経路の作り方を3つから選べるようにし、訪問順の計算の詳細（点数の付け方・複数案の出し方）は要件定義書で検討するとしていた。要件定義書 v0.2 の15章 Q1 への回答で、次のとおり決まった。

### 決定
- **範囲**：MVPでは、行きたい場所リスト内のスポットを対象にした**1日分の回り方**を作る。リスト外のおすすめスポットの自動追加と、複数日への分割は扱わない。
- **対象数**：経路作成で選べるスポットは**最大8か所**とし、9か所以上は選択できないようにする。
- **計算方法**：8か所以下なので、訪問順は**全通り**（最大40,320通り）を計算する。近似の方法（2-opt など）は使わない。
- **点数の付け方**：先にユーザーが選ぶ「優先すること」の選択肢を決め、選択肢ごとに点数の重みを用意する。重みの初期値は要件定義書 11章に置き、実装後に初期データ（金沢）で試して調整する。
- **複数案**：「移動が最も少ない案」「回れる場所が最も多い案」「おすすめの時間帯に最も合う案」の最大3案を出す。

### 理由
- 1日分・最大8か所に絞ると、全通りを計算しても数秒以内に終わり、必ず最も良い順番が見つかる。近似の方法を作る必要がなくなる。
- ハッカソンまで時間がないため、基本の画面と機能を先に作り、点数の重みは実際に動かしながら調整する。

### 影響
- 要件定義書の F-5-1（対象スポットの上限）、11章（計算手順）、13章（性能目標）を変更する。
- リスト自体には最大30スポットまで入れられるため、経路作成の画面で8か所を選んでもらう。

## ADR-0018：公共交通の移動時間が取得できない場合は概算で補う
- 状態：書き換え済み
- 日付：2026/10/22
- 書き換え元：—（ADR-0016 の補足）
- 書き換え先：ADR-0019

### 背景
ADR-0016 では、公共交通の移動時間を Google Routes API の行列で取得するとした。しかし、日本の公共交通の移動時間がこのAPIで取得できるかは、公式情報では確認しきれていない（旧 Directions API では、日本で公共交通の結果が返らないという報告がある）。取得できなかった場合の代わりを先に決めておく必要がある。

### 検討した案

| 案 | 内容 | 良い点 | 気になる点 |
| --- | --- | --- | --- |
| A. 徒歩・車のみにする | 公共交通をやめ、当日の公共交通は「ナビを開始」で Googleマップに任せる | 実装が最も簡単 | 車を持たない大学生には徒歩の時間しか出ず、離れたスポット（金沢港など）への移動時間が長くなりすぎて案が不自然になる |
| B. 概算で補う | 公共交通の移動時間を「直線距離 ÷ 時速15km ＋ 待ち時間10分」で出し、「目安」と表示する | 公共交通を前提にした案を作れる。外部APIを使わない | 実際の時刻表と食い違うことがある |

### 決定
**B とする。**
- 開発の最初に、金沢の数区間（金沢駅→兼六園、兼六園→ひがし茶屋街など）で Google Routes API から公共交通の移動時間が取得できるかを確認する。
- 取得できない場合、または区間ごとに結果が返らない場合は、その区間の公共交通の移動時間を「直線距離 ÷ 時速15km ＋ 待ち時間10分」で計算し、「目安」と表示する。時速15kmは、金沢の移動が路線バス中心であることに合わせた値。
- 徒歩・車は OpenRouteService を使い、Google Routes API には統一しない（無料枠の消費を抑えるため）。

### 理由
- 公共交通を前提にした案を出すことが、車を持たない大学生には重要なため。
- 当日の正確な乗換は「ナビを開始」で Googleマップに任せるため（ADR-0016）、計画段階では目安で十分なため。

### 影響
- 経路案のレスポンスで、概算した区間に印（`estimated`）を付け、画面に注意書きを出す。
- 金沢以外の地域では速度の値が合わない可能性があるため、他の地域のデータを入れるときに見直す（要件定義書 16章）。

## ADR-0019：移動時間は徒歩・車・公共交通とも Google Routes API（Essentials）で取得し、区間ごとに移動手段を選べるようにする
- 状態：承認済み
- 日付：2026/10/23
- 書き換え元：ADR-0016、ADR-0018

### 背景
ADR-0016 では、公共交通は Google Routes API、徒歩・車は OpenRouteService で移動時間の行列だけを取得し、移動手段は経路作成全体で1つとしていた。ADR-0018 では、公共交通の移動時間が取れない場合に概算で補うとしていた。
実際の道路や交通機関を考えた正確なプランを作りたい、区間ごとに移動手段を変えたい、という要望が出た。また Google Maps Platform には SKU（Essentials / Pro / Enterprise）ごとの無料枠があり、どの等級で使うかを決める必要がある。

### 検討した案

| 案 | 内容 | 良い点 | 気になる点 |
| --- | --- | --- | --- |
| A. 今のまま（公共交通は Google、徒歩・車は OpenRouteService。移動手段は全体で1つ） | ADR-0016・0018 のとおり | 無料枠が大きい | 区間ごとに移動手段を変えられない。API が2種類になる |
| B. Google Routes API に一本化（Essentials）。区間ごとに移動手段を選べる | 徒歩・車・公共交通とも Google の Essentials で取得する | 3つの移動手段とも同じ基準の正確な時間になる。API が1つで実装と無料枠の管理が簡単 | Google の無料枠の消費が増える |
| C. B に加えて車は渋滞を考える（Pro） | 車だけ `TRAFFIC_AWARE` を使う | 車の時間がより正確 | Pro は無料枠が5,000件と小さい。旅行の計画には渋滞予測までは不要 |

### 決定
**B とする。**
- **API と等級**：移動時間は徒歩・車・公共交通とも Google Routes API の **Essentials** だけで取得する。Pro・Enterprise に上がらないよう、次を守る。
  - 車は渋滞を考えない計算（`routingPreference: TRAFFIC_UNAWARE`）にする。
  - 返してもらう項目（`X-Goog-FieldMask`）は所要時間・距離・状態だけにする（通行料金などは取らない）。
  - 経由地は使わず、区間ごとに呼ぶ。
  - 出発時刻は公共交通だけに渡す。
- **計画の流れ**
  1. 経路案を作るときは、ユーザーが選んだ移動手段で移動時間の行列を1回だけ取得する（Compute Route Matrix Essentials。最大10地点×10地点）。この値で訪問順と最大3案を作る（ADR-0017）。
  2. 案を選んだら、公共交通の区間だけ実際の出発時刻で取り直す（Compute Routes Essentials。1区間1回）。
  3. ユーザーはタイムラインの区間ごとに移動手段（徒歩・車・公共交通）を変えられる。変えた区間だけ取り直し、以降の時刻を計算し直す。訪問順は変えない。
- **地図**：OpenFreeMap の地図に、訪問順にスポットを結んだ線を描く（今のまま）。Google の経路の形は取得せず、Google 以外の地図に描かない（Google の利用規約）。
- **保存**：Google から取得した移動時間はその計画の間だけ使い、移動時間のキャッシュ（`travel_time_cache`）には保存しない（Google の利用規約）。
- **公共交通が取れない場合**：日本の公共交通が API で取れない、または区間ごとに結果が返らない場合は、その区間を「直線距離 ÷ 時速15km ＋ 待ち時間10分」の概算で出し、「目安」と表示する（旧 ADR-0018 の考え方を引き継ぐ）。
- **当日の道案内**：保存した経路プランの各区間に「ナビ開始」ボタンを置き、その区間の移動手段（walking / driving / transit）を指定した Google マップの URL を開く（APIキー不要・無料）。
- **出典の表示**：タイムラインに「所要時間：Google マップ（Routes API）」と表示する。

### 理由
- 3つの移動手段の所要時間を同じ基準（Google）でそろえることで、区間ごとに移動手段を変えても比べやすく、正確なプランになる。
- やりたいこと（所要時間・距離・公共交通の出発時刻）はすべて Essentials で足り、Essentials は無料枠が最も大きい（SKU ごとに毎月10,000件。数値は公式で要確認）。
- API が1つになり、実装と無料枠の管理が簡単になる。

### 影響
- OpenRouteService は使わなくなる（ADR-0020）。環境変数 `ORS_API_KEY` を削除し、無料枠は `GOOGLE_ROUTE_MATRIX_MONTHLY_FREE` と `GOOGLE_ROUTES_MONTHLY_FREE` で管理する。
- 無料枠の消費の目安：経路作成1回で、行列が最大100件、区間の取り直しが約10回。行列の無料枠が10,000件なら、80%で止める設定で月におよそ80回の計画が作れる。
- API に `POST /api/v1/plans/legs`（区間ごとの所要時間の取り直し。最大10区間）を追加する。
- `travel_time_cache` テーブルは使わない（削除はしない）。
- 日本の公共交通が Routes API で取れるかは、キーができ次第、金沢の数区間で確認する。
- Google Cloud にお支払い情報の登録が必要になる（無料枠内なら請求は発生しない）。Google Cloud 側でも1日の上限（割り当て）を設定する。
- Google の利用規約（帰属表示、Google 以外の地図との併用、保存）は、公開前にもう一度確認する。

## ADR-0020：技術スタック（経路APIを Google Routes API に一本化）
- 状態：承認済み
- 日付：2026/10/23
- 書き換え元：ADR-0013

### 背景
ADR-0019 で、移動時間を徒歩・車・公共交通とも Google Routes API で取得することにしたため、ADR-0013 の技術スタックのうち経路・移動時間の部分が変わる。

### 決定

| 領域 | 採用 |
| --- | --- |
| フロントエンド / API | Next.js（App Router）＋ TypeScript |
| スタイル / アイコン | Tailwind CSS / lucide-react |
| 地図 | MapLibre GL JS ＋ OpenFreeMap、クラスタは Supercluster（ブラウザ側） |
| 認証・DB・ストレージ | Supabase（Auth / PostgreSQL＋PostGIS / Storage） |
| 経路・移動時間 | **Google Routes API（Essentials）**：徒歩・車・公共交通（ADR-0019） |
| 当日の道案内 | Google マップの URL（Maps URLs。APIキー不要） |
| 場所検索 | 自前DB → Nominatim |
| AI | Gemini API（無料枠。β版） |
| ホスティング / 監視 / バックアップ | Vercel / Sentry / GitHub Actions ＋ Cloudflare R2 |

### 理由
- ADR-0013 の理由（画面とAPIを1つのリポジトリで作れる、PostGIS と RLS、無料・キー不要の地図）はそのまま。
- 経路APIを1つにまとめることで、実装と無料枠の管理が簡単になる（ADR-0019）。

### 影響
- OpenRouteService のアカウント作成・キーの発行は不要になる（セットアップ手順から削除）。

## ADR-0021：ログインをメールアドレス＋パスワード（確認メールあり）にし、確認メールは Gmail の SMTP で送る
- 状態：承認済み
- 日付：2026/10/24
- 書き換え元：—（要件定義書 v0.6 の F-6-1「Googleログインのみ」を変更する）

### 背景
- これまでは Googleログインだけにしていた（F-6-1）。そのため Googleアカウントを持っていない人は使えない。また、Google の同意画面が「テスト」のままだと、登録したテストユーザーしかログインできない。
- ハッカソンの審査員や来場者にも、その場で登録して使ってもらいたい。
- 費用はハッカソンの間だけでよく、無料枠の範囲に収めたい。
- Supabase Auth は標準でメールアドレス＋パスワードに対応している。ただし標準のメール送信は、プロジェクトのメンバーのアドレス宛てにしか届かず、1時間あたりの送信数もごく少ない。

### 検討した案

| 案 | 長所 | 短所 |
| --- | --- | --- |
| A. メール＋パスワード（確認メールなし） | Supabase の設定を1つ変えるだけ | 他人のメールアドレスでも登録できる |
| B. メール＋パスワード（確認メールあり）＋ Supabase 標準のメール送信 | 設定が簡単 | メンバー以外に確認メールが届かない |
| C. メール＋パスワード（確認メールあり）＋ Gmail の SMTP | 誰にでも確認メールが届く。無料（1日500通）。独自ドメインが不要 | チームの Gmail に2段階認証とアプリパスワードが必要 |
| D. メール＋パスワード（確認メールあり）＋ Resend | 送信元を独自ドメインにできる | 独自ドメインがないと自分宛てにしか送れない |
| E. 認証を Clerk・Firebase Authentication などに替える | 確認メールもサービス側で送れる | DBのユーザーID・権限（RLS）が Supabase Auth 前提のため、作り直しになる |

### 決定
- 案Cを採用する。認証は Supabase Auth のまま、メールアドレス＋パスワードで登録・ログインする。
- 確認メールは、チーム用の Gmail アカウントのアプリパスワードを使い、Supabase の「カスタムSMTP」から送る（`smtp.gmail.com`、ポート465）。
- 確認メールのリンクは token_hash 方式（`/auth/confirm?token_hash=...&type=email`）にする。登録した端末と別の端末（スマホで登録してPCでメールを開くなど）でリンクを開いても確認できるようにするため。
- パスワードは8文字以上（Supabase の「Minimum password length」と画面の両方で設定）。
- Googleログインは任意とし、Supabase に設定した場合だけ `NEXT_PUBLIC_ENABLE_GOOGLE_LOGIN=true` でボタンを表示する。
- パスワードの再設定画面はMVPでは作らない。忘れた場合は管理者が Supabase の画面で対応する。

### 理由
- アプリのDB・権限・APIを変えずに、誰でも登録できるようになる。
- 無料で、独自ドメインも不要。ハッカソンの規模（数十〜数百人）なら1日500通で足りる。

### 影響
- Supabase の設定：Email プロバイダーを有効、「Confirm email」をオン、カスタムSMTPに Gmail を設定、「Confirm signup」のメール文面のリンクを `/auth/confirm` に変更、URL Configuration の Site URL を公開URLにする。
- 確認メールは Gmail アカウントから送られるため、迷惑メールのフォルダに入ることがある。画面に「迷惑メールのフォルダも確認」と案内する。
- Gmail のアプリパスワードは Supabase の設定にだけ置き、リポジトリやチャットに書かない。
- 要件定義書を v0.7 に更新する（F-6-1・F-6-2・S-14・1.10・14章）。
