# セットアップ手順（チームで設定するもの）

アカウントの作成やキーの発行は、メンバーのアカウントで行う必要があるため、この手順でチームが設定してください。キーはすべて `.env.local`（Git に入らない）と、Vercel・GitHub の Secrets にだけ入れます。チャットやリポジトリには貼らないでください。

キーがなくても `npm run dev` で地図とスポット詳細は確認できます（金沢のデモデータが表示されます）。

## 目次

| 順番 | やること | 所要時間の目安 | これで使えるようになるもの |
| --- | --- | --- | --- |
| 1 | Supabase プロジェクトを作る | 15分 | DB・写真の保存 |
| 2 | DB のテーブルを作る | 10分 | 全機能の土台 |
| 3 | ログイン（メール＋パスワード、確認メール）を設定する | 20分 | ログイン・投稿・リスト・経路作成 |
| 4 | `.env.local` を書く | 5分 | ローカルでの動作 |
| 5 | 金沢の初期データを入れる | 5分 | 地図に金沢のスポットが出る |
| 6 | 経路APIのキーを用意する（Google Routes API） | 20分 | 実際の道路・交通機関を考えた経路作成 |
| 7 | Vercel で公開する | 15分 | スマホからのアクセス・デモ |
| 8 | バックアップを設定する | 20分 | 毎日のバックアップ |

## 1. Supabase プロジェクトを作る

1. https://supabase.com にログインし、「New project」を押す。
2. 次のように入力する。
   - Name：`tabi-dokoikou`（任意）
   - Database Password：強いパスワードを作り、チームのパスワード管理ツールに保存する
   - Region：**Northeast Asia (Tokyo)**
   - Plan：Free
3. 作成後、「Project Settings」→「API Keys」（または「API」）を開き、次の3つを控える。
   - Project URL（`https://xxxx.supabase.co`）
   - `anon` `public` キー（新しい画面では「Publishable key」）
   - `service_role` キー（新しい画面では「Secret key」）。**サーバー専用。絶対に公開しない**

## 2. DB のテーブルを作る

どちらかの方法で、`supabase/migrations/` の SQL を実行します。

**方法A：SQL エディタに貼る（かんたん）**

1. Supabase の「SQL Editor」を開く。
2. `supabase/migrations/20261024000000_init.sql` の中身を全部貼って「Run」。
3. 続けて `supabase/migrations/20261024000100_cron.sql` も同じように実行する。
4. 「Table Editor」に `spots` `posts` などが、「Storage」に `post-images` バケットができていれば成功。

**方法B：Supabase CLI（今後の変更も管理しやすい）**

```bash
npx supabase login
```

```bash
npx supabase link --project-ref <Project URL の xxxx の部分>
```

```bash
npx supabase db push
```

> pg_cron（定期処理）でエラーになった場合は、「Database」→「Extensions」で `pg_cron` を有効にしてから、もう一度実行してください。

## 3. ログイン（メールアドレス＋パスワード、確認メールあり）を設定する

ログインはメールアドレス＋パスワードで行い、登録時に確認メールを送ります（ADR-0021）。Supabase 標準のメール送信はプロジェクトのメンバー宛てにしか届かないため、確認メールはチームの Gmail から送ります。

### 3-1. Gmail のアプリパスワードを作る

1. 確認メールの送信元にする Gmail アカウントを用意する（チーム用に新しく作るのがおすすめ）。
2. https://myaccount.google.com/security で「2段階認証プロセス」をオンにする。
3. https://myaccount.google.com/apppasswords でアプリ名（例：`tabi-dokoikou`）を入れて作成し、表示された16文字のパスワードを控える（チャットやリポジトリには貼らない）。

### 3-2. Supabase のメール送信を Gmail にする

「Authentication」→「Emails」→「SMTP Settings」で「Enable custom SMTP」をオンにして、次を入れて保存する。

| 項目 | 値 |
| --- | --- |
| Sender email | 3-1 の Gmail アドレス |
| Sender name | `旅行どこいこう` |
| Host | `smtp.gmail.com` |
| Port number | `465` |
| Username | 3-1 の Gmail アドレス |
| Password | 3-1 のアプリパスワード（空白なしの16文字） |

保存後、「Authentication」→「Rate Limits」で「Rate limit for sending emails」を 30（1時間あたり）程度にする（Gmail は1日500通まで）。

### 3-3. メール＋パスワードの登録を有効にする

1. 「Authentication」→「Sign In / Providers」→「Email」を開き、次のようにして保存する。
   - Enable Email provider：オン
   - Confirm email：オン
   - Minimum password length：`8`
2. 「Authentication」→「Emails」→「Templates」→「Confirm signup」を開き、本文のリンクを次に変えて保存する（登録した端末と別の端末でメールを開いても確認できるようにするため）。

```html
<h2>旅行どこいこう の登録を完了してください</h2>
<p>下のリンクを開くと、登録が完了します。</p>
<p><a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email">登録を完了する</a></p>
<p>心当たりがない場合は、このメールを無視してください。</p>
```

件名（Subject）は `旅行どこいこう：登録の確認` などにする。

### 3-4. URL を登録する

「Authentication」→「URL Configuration」

- Site URL：公開URL（例：`https://kz-2609.vercel.app`）。確認メールのリンクはこのURLを使う。
- Redirect URLs に次を追加：
  - `https://<公開URL>/auth/callback`
  - `http://localhost:3000/auth/callback`

> 確認メールのリンクは Site URL（公開URL）に向くため、ローカルで登録した場合も、リンクを開くと公開URLで確認が完了します。

### 3-5.（任意）Google ログインも使う

1. Google Cloud の「Google Auth Platform」で同意画面と OAuth クライアント（ウェブアプリケーション）を作る。承認済みのリダイレクト URI は `https://<xxxx>.supabase.co/auth/v1/callback`。
2. Supabase の「Authentication」→「Sign In / Providers」→「Google」で、クライアント ID とシークレットを入れて有効にする。
3. Vercel と `.env.local` の `NEXT_PUBLIC_ENABLE_GOOGLE_LOGIN` を `true` にして、デプロイし直す。

## 4. `.env.local` を書く

```bash
cp .env.example .env.local
```

`.env.local` を開き、1で控えた値を入れます。

| 変数 | 入れる値 |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon（Publishable）キー |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role（Secret）キー |
| `NOMINATIM_USER_AGENT` | `tabi-dokoikou (チームの連絡先メール)`（OpenStreetMap の場所検索の利用規約で必要） |
| `USE_MOCK_EXTERNAL_APIS` | 6が終わるまでは `true`（移動時間を直線距離から概算） |

保存したら開発サーバーを起動し直します。

```bash
npm run dev
```

http://localhost:3000/login の「新規登録」で登録し、確認メールのリンクを開いてログインできれば成功です。初回は表示名の確認画面が出ます。

## 5. 金沢の初期データを入れる

1. 4で、メンバーが一度ログインしておく（投稿者がいないと入りません。ログインしたメンバーに順番に割り当てられます）。
2. Supabase の「SQL Editor」で `supabase/seed/kanazawa.sql` の中身を貼って「Run」。
3. 地図で金沢を表示し、写真の束やピンが出れば成功（写真はまだないので、カテゴリのアイコンで表示されます）。

> `supabase/seed/users.sql`（テストユーザー）はローカル開発用です。本番の Supabase では実行しないでください。
>
> 写真はあとでチームが用意します（要件定義書 10.5）。スポットの緯度経度はおおよその値なので、写真を入れるときに確認してください。

## 6. 経路APIのキーを用意する（Google Routes API・Essentials）

徒歩・車・公共交通の所要時間は、すべて Google Routes API の **Essentials** で取得します（ADR-0019）。

### 6-1. キーを作る

1. 3-1 と同じ Google Cloud プロジェクトで「お支払い」を設定する（Routes API の利用に必要。無料枠の範囲なら請求は発生しません）。
2. 「APIとサービス」→「ライブラリ」で **Routes API** を有効にする。
3. 「認証情報」→「API キーを作成」。作ったキーの「API の制限」で Routes API だけを許可する。
4. 「APIとサービス」→「Routes API」→「割り当て」で、1日の上限を小さめに設定する（例：行列は1日 300 件、経路は1日 100 回。F-8-6）。
5. `.env.local` の `GOOGLE_ROUTES_API_KEY` に入れる。
6. 無料枠の件数を公式の料金ページで確認し、次に入れる（80%で自動停止します）。
   - `GOOGLE_ROUTE_MATRIX_MONTHLY_FREE`：Compute Route Matrix Essentials の毎月の無料件数（組み合わせ1件ごと）
   - `GOOGLE_ROUTES_MONTHLY_FREE`：Compute Routes Essentials の毎月の無料件数（1回ごと）

> アプリは Pro・Enterprise に上がらないよう、車は渋滞を考えない計算にし、返してもらう項目を所要時間・距離・状態だけにしています。使い始めたら、Google Cloud の「お支払い」→「レポート」で、実際に **Essentials** の SKU で数えられているかを確認してください。

### 6-2. 実際のAPIに切り替えて確認する

1. `.env.local` の `USE_MOCK_EXTERNAL_APIS` を `false` にして開発サーバーを起動し直す。
2. リストに金沢駅・兼六園・ひがし茶屋街などを入れ、移動手段「公共交通」で経路案を作る。
3. 案を選ぶと、公共交通の区間が実際の出発時刻で取り直されます。
4. 「公共交通の移動時間を取得できなかった区間は、概算で計算しています」と出た場合は、日本の公共交通が Routes API で取れていません。そのまま概算で動きます（ADR-0019）。結果をチームで共有してください。
5. タイムラインの区間ごとに「徒歩・車・公共交通」を切り替えて、所要時間が変わることも確認してください。

> 開発中は `true` に戻しておくと、無料枠を使いません（F-8-8）。

## 7. Vercel で公開する

1. https://vercel.com で「Add New」→「Project」→ `jphacks/kz_2609` を選んで Import。
   - 一覧に出ない場合は、Vercel の GitHub アプリを jphacks 組織に入れる必要があり、組織の管理者の許可がいります。許可が出ないときは、下の「（補足）Vercel CLI で公開する」を使ってください。
2. Framework Preset は Next.js のまま。
3. 「Environment Variables」に `.env.local` と同じ値を入れる（`NEXT_PUBLIC_ENABLE_GOOGLE_LOGIN` は Google を設定するまで `false`）。
4. Deploy。表示されたURLを、3-2 の Site URL と Redirect URLs（`https://<URL>/auth/callback`）に追加する。

## 8. バックアップを設定する（ADR-0011）

1. Cloudflare（https://dash.cloudflare.com）で R2 を有効にし、バケット（例：`tabi-backup`）を作る。
   - バケットの「設定」→「オブジェクトのライフサイクル」で、30日より古いオブジェクトを削除するルールを追加する。
2. R2 の「API トークンを管理」で、そのバケットに読み書きできるトークンを作り、Access Key ID と Secret Access Key を控える。
3. Supabase の「Project Settings」→「Database」→「Connection string」で URI（Session pooler）を控える（パスワード入り）。
4. Supabase の「Project Settings」→「Storage」→「S3 Access Keys」でキーを作る（写真のバックアップ用）。
5. GitHub のリポジトリ →「Settings」→「Secrets and variables」→「Actions」に次を登録する。

| Secret | 値 |
| --- | --- |
| `SUPABASE_DB_URL` | 3 の接続URI |
| `BACKUP_PASSPHRASE` | バックアップを暗号化する長いパスワード（管理担当者が保管。失うと復元できない） |
| `R2_ACCOUNT_ID` | Cloudflare のアカウントID |
| `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` | 2 のキー |
| `R2_BUCKET` | バケット名 |
| `SUPABASE_PROJECT_REF` | Project URL の `xxxx` の部分 |
| `SUPABASE_S3_ACCESS_KEY_ID` / `SUPABASE_S3_SECRET_ACCESS_KEY` | 4 のキー |
| `NEXT_PUBLIC_SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` | 1 の値（一時ファイル削除用） |

6. 「Actions」タブで `db-backup` を選び、「Run workflow」で手動実行して成功するか確認する。

## （任意）ローカルの Supabase を使う

Docker Desktop があれば、ローカルに Supabase を立てて、テストユーザーで動作確認できます。

```bash
npx supabase start -x realtime,edge-runtime,logflare,vector,supavisor
```

表示された `API URL`・`anon key`・`service_role key` を `.env.local` に入れると、テストユーザー（`supabase/seed/users.sql` に記載）でログイン画面からログインできます。

> 開発用PCでは Docker Desktop がイメージを取得できず（`public.ecr.aws` などへの接続がタイムアウト）、ローカルの Supabase を起動できませんでした。Docker Desktop の「Settings」→「Resources」→「Proxies」の設定や、ネットワーク・セキュリティソフトの設定を確認してください。
