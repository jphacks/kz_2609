## 製品概要

### 背景(製品開発のきっかけ、課題等）

友達との旅行で「幹事」を任されると、計画のほとんどを1〜2人で背負うことになります。私たち自身も、行き先を探すのは楽しいのに、「どこを・どの順で・何時に回るか」を決める段階で何度も疲れてしまいました。

旅行の計画は、大きく2つの作業に分けられます。

| 作業 | 内容 | 性質 |
| --- | --- | --- |
| ① どこに行くかを決める | 写真や雰囲気を見て「ここに行きたい」を選ぶ | **一番楽しい**。ただし情報が散らばっていて探しにくい |
| ② どう回るかを決める | 移動時間・滞在時間・時間帯を考えて、順番と時刻を決める | **一番大変**。計画疲れや「当日回りきれない」の原因になる |

実際に、国内旅行で「失敗・やらかし」を経験した人は76.0%、**旅行の計画段階でストレス（計画疲れ）を感じている人は約7割**にのぼります（[PR TIMES の調査](https://prtimes.jp/main/html/rd/p/000000001.000034728.html)）。

### 既存サービス

既存のサービスでは、この2つの作業がうまくつながっていません。

| サービス | 得意なこと | 足りないこと |
| --- | --- | --- |
| Google マップ | 1区間の経路検索。気になった場所を「保存済み」のリストに登録しておける | 地図上の場所は名前（文字）で並ぶだけで、どんな場所かは1つずつ開いて調べるまでわからない。保存した場所を回る順番・滞在時間・時間帯は考えてくれない |
| Instagram | 写真で現地の雰囲気がわかる | 場所が地図上にまとまっておらず、計画に使えない |
| AI による旅程作成 | 行き先ごと提案してくれる | 一番楽しい「行き先選び」までAIが決めてしまう。なぜその順番なのかが見えない |
| Mappito AI Trip Planner & Maps | 旅程をAIで自動作成できる。場所の詳細で写真を見られる | 写真は、場所を選んだあとに詳細で確かめるためのもの。地図を写真で眺めながら行き先を探す使い方にはなっていない |

Google マップも旅程作成アプリも、地図の上ではどんな場所なのかがわかりません。そのため、**「どこに行きたいか」を別のところで調べ終えた人が、計画の段階で使う道具**になっています。旅行で一番楽しい「行き先を選ぶ」段階を、地図の上で支えるサービスはまだありません。

そこで私たちは、**あえてすべてを自動化しない**ことにしました。楽しい「① 選ぶ」は人の手に残し、大変な「② 回り方を決める」だけを自動にします。

### 製品説明（具体的な製品の説明）

1. **探す**：地図を開くと、日本全体から写真の束（しずく形のピンの中に代表写真、下に「名前 +その他N件」）が並び、近づくと1スポットずつの写真ピンに切り替わります。投稿は少ないのにいいねが多い場所は「隠れた名所」として目立たせます。
2. **見る**：ピンを選ぶと、実際に行った人の写真・コメント・投稿が多い時間帯・滞在時間の目安がわかります。
3. **比べる**：気になった場所を「行きたい場所リスト」に集め、ホテルや駅からの距離で並べ替えたり、最大8件を横並びで見比べたりできます。
4. **共有する**：リストの共有URLを発行して LINE などで送ると、一緒に旅行する友達がログインなしで閲覧できます（編集はできません）。
5. **回り方を作る**：リストから「経路を作成」を押すと、滞在時間・おすすめの時間帯・昼食休憩（時間帯と長さを選べる）を考えた1日の回り方を最大3案作ります。公共交通の区間は「何分歩いてどの乗り場へ・どの路線に乗り・どこで降りるか」までタイムラインに出します（石川県のバス・鉄道）。
6. **AIと相談する**：「夕日は金沢港で見たい」「歩くのは少なめがいい」のような細かい希望は、AIが条件に置き換え、それを満たす回り方を作ります。
7. **当日**：区間ごとに移動手段（徒歩・車・公共交通）を変えられます。保存したプランは、経由地を含めた1日の全体を1本の Google マップの経路で開けるほか、区間ごとの「ナビ開始」から道案内を開けます。
8. **投稿する**：旅行中に写真とコメントをその場で投稿すると、次の旅行者のための地図とデータが育ちます。

### 特長・競合優位性

#### 1. あえて全部を自動化しない：「選ぶ楽しさ」はそのままに、「回り方」だけを自動に

行き先は、写真で人気がひと目でわかる地図から自分で選びます。投稿の多さを数字ではなく、写真の束の「+その他N件」と写真ピンの枠の色で表すので、眺めているだけで「ここに行きたい」が見つかります。大変な回り方の計算だけを、ボタン1つで引き受けます。

#### 2. 前の旅行者の投稿が、次の旅行者の計画を助ける

投稿の滞在時間の中央値から「その場所に何分いるか」を、投稿時刻の分布から「何時ごろに行くとよいか（例：夕日の時間）」を決めます。投稿が集まるほど地図と回り方の精度が上がり、旅行は自分だけの経験ではなく、**次の旅行者へのバトン**になります。投稿は少ないが満足度の高い「隠れた名所」を目立たせることで、人気の場所への集中も分散します。

#### 3. 計画は数秒、当日まで迷わない

訪問順を全通り調べ（8か所で約11万通りを1秒以内）、「移動が少ない」「たくさん回る」「おすすめの時間帯に合わせる」の3つの観点で特徴の違う案を出します。徒歩・車の所要時間は Google Routes API で実際の道路を考えて計算し、当日は Google マップの道案内に引き継ぎます。

#### 4. Google マップと Instagram の強みだけを掛け合わせた、ほかにない地図

地図には、場所の名前ではなく**写真**が並びます。ピンの先頭の写真と枠の色、写真の束の「+その他N件」で、人気の場所はどこか、どんな雰囲気の場所かが、調べなくても目に入ってきます。Instagram のように受け身で眺めて楽しみながら、Google マップのように「この距離なら回れるか」を考えて選べます。

- **寄り道が見つかる**：目当ての場所のまわりにある、ほかの場所の写真も自然に目に入ります。近くの寄り道を予定に入れられるので、旅行の満足度が上がり、「近くにあったのに行きそびれた」という後悔がなくなります。
- **選んだあとで「回れない」がわからない**：行き先を地図の上で選ぶので、場所どうしの距離感を見ながら選べます。計画の段階になって「この組み合わせは1日では無理」と判明して選び直す、ということが起きません。

#### 5. AI に任せるのは「希望を条件に置き換える」ところまで

「夕日は金沢港で見たい」のような細かい希望は「AIと相談」で伝えられますが、AI が決めるのは条件（時刻の指定・順番の希望・除外・ペースなど）だけです。回る順番は自前の全通り計算で決めるので、AI が存在しない場所や回れない順番を作ることがなく、なぜその順番なのかを説明できます。

#### 6. 公共交通も「どこから何に乗るか」まで

Google の経路 API は日本の電車・バスの経路を返しません。そこで、国土数値情報（国土交通省）の停留所・駅・路線のデータから、自前で乗り換えを探します。城下まち金沢周遊バス・石川県の路線バス（219系統）・県内の鉄道に対応し、「徒歩何分でどの乗り場へ・どの路線に乗り・どこで降りるか」を手順として出します。歩いた方が早い区間は徒歩に、1時間以上歩く区間は車（タクシーなど）をすすめます。時刻表のデータは利用条件で使えないため、利用条件を守れるデータだけで作っています。

#### 7. 友達との相談も、当日の移動も1本でつながる

リストは共有URLを1つ送るだけで、友達がログインなしで見られます。保存したプランは、経由地を含めた1日の全体を Google マップの1本の経路で開けるので、当日に次の目的地を毎回検索し直す必要がありません。

#### 8. 自分たちの旅行に合わせて細かく直せる

「必ず行きたい」場所と拠点（ホテル・駅）の指定、拠点からの距離での並べ替え、最大8件の比較、昼食休憩の時間帯と長さ、区間ごとの移動手段（徒歩・車・公共交通）の切り替えができます。直したところだけを計算し直すので、すぐに結果が変わります。

### 解決出来ること

| 段階 | これまで | TravelSeek では |
| --- | --- | --- |
| 行き先を決める | 文字中心の観光サイトや SNS を行き来して探す | 写真と投稿の多さで、地図から直感的に選べる。近くの寄り道も目に入る |
| 回り方を決める | 移動・滞在・昼食・時間帯を手作業で組み合わせる | ボタン1つで、無理のない1日の回り方が最大3案できる |
| 公共交通を調べる | 乗り換え案内で区間ごとに調べ直す | 乗り場・路線・降りる場所までタイムラインに出る |
| 友達と相談する | スクリーンショットや URL をばらばらに送る | リストの共有URLを1つ送るだけ |
| 当日 | 次の目的地を毎回検索し直す | 経由地を含めた1日の全体を、1本の Google マップの経路で開ける（区間ごとの「ナビ開始」もある） |

### 今後の展望

- スマートフォンのアプリ化（今はブラウザで使う Web アプリ）
- 都道府県・自治体と連携したキャンペーンで、ユーザーの入り口をつくる。「投稿すると観光施設の割引がもらえる」ことで投稿の動機をつくり、集まった投稿を見て新しい旅行者が訪れ、その人がまた投稿する、という旅行者・地域・観光施設のあいだで利益が循環する仕組みを実現する
- 公共交通の正確なデータ（時刻表・本数）を交通事業者からいただき、公共交通を使う旅行プランをより正確にする（徒歩・車は Google の道路データで正確に計算できている。公共交通の待ち時間・乗車時間は今は目安）
- 公共交通の乗り換えの計算を、石川県からほかの地域へ広げる
- 営業時間を考えた回り方の作成（営業時間外に着く案を出さない）
- 複数日の旅行プラン、日ごとの拠点の設定
- 共有したリストに友達が「行きたい」を付けられる共同編集
- 不適切な投稿の通報と管理の画面
- 金沢から始め、ほかの地域へ投稿を広げる（大学・サークルと連携した初期投稿の呼びかけ）

### 注力したこと（こだわり等）

- **AI に任せる範囲を絞りました。** AI には会話を条件に置き換えることだけを任せ、回る順番は自前の全通り計算で決めます。AI に順番まで考えさせるより正確で、なぜその順番なのかを説明できるためです。
- **UI の工夫。** 写真が主役の地図にするため、しずく形のピンの中に丸い写真を入れ、ズームに応じて写真の束（「+その他N件」）と1スポットずつの写真ピンを切り替えます。人気はピンの枠の色、隠れた名所は紫のリングで表し、数字を読まなくても眺めるだけでわかるようにしました。ピンを選んだときのシートや全画面の検索は、多くの人が使い慣れた Google マップに近い形にし、写真はタップで全画面に広げられます。
- **公共交通は、利用条件を守れるデータだけで作る。** 時刻表のデータは利用条件で案内サービスに使えないため、国土数値情報の停留所・駅・路線と Google の車の所要時間から乗車時間を出し、待ち時間は「目安」と明記しています。
- **地図を止めない。** 地図を動かしている間も区画ごとにデータを取りながらピンを描き続け、表示が途切れないようにしました。
- **個人情報を守る。** 写真はブラウザで縮小し、位置情報などの EXIF をすべて消してからアップロードします。リストの共有URLは推測できない乱数で、いつでも停止できます。AI には会話とスポット名だけを送り、会話は保存しません。
- **無料枠の中で運用する。** 外部サービスの利用量を数え、無料枠の80%に達したらその機能だけを自動で止めます。
- **スマホの片手操作。** 44px 以上のタップ領域にし、画面の端を上下になぞるだけで地図を拡大・縮小できるようにしました。

## 開発技術

### 活用した技術

#### API・データ

- Google Routes API（Compute Route Matrix / Compute Routes の Essentials）：徒歩・車の所要時間と、バスの乗車時間のもとになる車の所要時間（日本の電車・バスの経路は返らないため、公共交通（TRANSIT）は使わない）
- 国土数値情報（国土交通省、CC BY 4.0）のバス停留所データ（2022年）・鉄道データ（2024年）：公共交通の乗り換えの計算
- Google マップ URL：当日の道案内（1日の全体を1本で開く経路と、区間ごとの「ナビ開始」）
- Gemini API（無料枠）：「AIと相談」で会話を回り方の条件に置き換える
- OpenFreeMap：背景地図
- OpenStreetMap Nominatim：スポット名から場所を検索
- Supabase（PostgreSQL・PostGIS・Auth・Storage・pg_cron）
- 112スポットの初期データ（石川県32＝金沢市28・市外4、東京・京都・大阪 各10、北海道・宮城・神奈川・長野・静岡・奈良・兵庫・広島・福岡・沖縄 各5）と、Wikimedia Commons のクリエイティブ・コモンズ等の写真（作者・ライセンスは `/credits` と各写真の下に表示）

#### フレームワーク・ライブラリ・モジュール

- Next.js 16（App Router）、React 19、TypeScript、Tailwind CSS v4
- MapLibre GL JS、Supercluster（写真の束のまとめ）
- zod（入力チェック）、Lucide（アイコン）、heic2any（iPhone の写真の変換）
- Vitest（経路計算・公共交通の乗り換え・AIの返答の検証・共有URL・隠れた名所などのテスト）
- Vercel（公開）、GitHub Actions・Cloudflare R2（バックアップ）

#### デバイス

- スマートフォンのブラウザ（GPS・カメラロール・共有シート）
- PC のブラウザ

- **AIと相談**：AI には会話を条件（時刻の指定・順番の希望・除外・ペースなど）に置き換えることだけを任せ、回り方は自前の全通り計算で作ります。AI の返答はリスト内のスポットと決まった値に絞って検証します（[src/lib/plan-chat.ts](src/lib/plan-chat.ts)、[src/app/api/v1/plans/chat/route.ts](src/app/api/v1/plans/chat/route.ts)、commit [0f0fa7b](https://github.com/jphacks/kz_2609/commit/0f0fa7b)、[6c8cf22](https://github.com/jphacks/kz_2609/commit/6c8cf22)）。
- **公共交通の乗り換えの計算**：国土数値情報の停留所・駅・路線から、「徒歩 → 乗り場 → 乗車（乗り換えは1回まで）→ 降り場 → 徒歩」の最も早い行き方をダイクストラ法で探し、タイムラインに手順を出します。城下まち金沢周遊バス・石川県の路線バス219系統（停留所 約4,000か所）・県内の鉄道に対応し、鉄道は線路の道のりで乗車時間を出します。歩いた方が早い区間は徒歩に、1時間以上歩く区間は車をすすめ、自動で決めた区間もあとから公共交通を選び直せます（[src/lib/transit/](src/lib/transit/)、[scripts/build-transit-data.mjs](scripts/build-transit-data.mjs)、ADR-0026・0027、commit [ac4dc22](https://github.com/jphacks/kz_2609/commit/ac4dc22)、[5c05a97](https://github.com/jphacks/kz_2609/commit/5c05a97)、[b22772f](https://github.com/jphacks/kz_2609/commit/b22772f)、[9f03c43](https://github.com/jphacks/kz_2609/commit/9f03c43)、[4b695d0](https://github.com/jphacks/kz_2609/commit/4b695d0)）。
- **1日の全体を1本で開く Google マップの経路**：保存したプランの出発地から到着地までを、訪問順の経由地でつないだ1本の経路として開きます（commit [20f518b](https://github.com/jphacks/kz_2609/commit/20f518b)）。
- **昼食休憩の時間帯と長さ**：選んだ時間帯の中に、選んだ長さの昼食休憩を入れて回り方を作ります（commit [d67fb98](https://github.com/jphacks/kz_2609/commit/d67fb98)、[cb19db7](https://github.com/jphacks/kz_2609/commit/cb19db7)）。

## 開発のルール

- アイコンは Lucide だけを使い、絵文字は使わない（要件定義書 8.1）。
- 片側だけに色の線を付けるカード（border-left のアクセント）は使わない（8.2）。
- APIキーはサーバー側の環境変数だけに置き、リポジトリに入れない。
- 開発中は `USE_MOCK_EXTERNAL_APIS=true` にして、外部APIの無料枠を使わない。
- Next.js 16 を使っているため、書き方は `node_modules/next/dist/docs/` を確認する（AGENTS.md）。

### コミットのルール

審査で開発の流れを追いやすくするため、次のようにコミットします。

- **1つの機能・1つの修正を1コミットにする。** 関係のない変更（別の機能、ついでの整形など）は混ぜず、分けてコミットする。
- **その機能に関わる変更は同じコミットにまとめる。** 画面・API・DB・テスト・資料（要件定義書・ADR）の更新を、別々のコミットに分けない。
- **1行目は「何をしたか」を日本語で書く。** 例：`経路作成に「AIと相談」（Gemini）を追加する`、`スポットの投稿一覧が取得できない不具合を直す`
- **2行目は空けて、3行目から理由と中身を書く。** なぜ変えたか、主な変更点、関係する要件（`F-5-5` など）や ADR の番号を書く。
- **DB の変更は `supabase/migrations/` に新しいファイルを追加する。** 既存のマイグレーションは書き換えない（main に push すると Supabase に自動で反映される）。
- **push の前に確認する。** `npm run typecheck`・`npm run lint`・`npm test` が通ること。
- **main に直接 push する。** 拒否されたら `git pull --rebase origin main` で取り込んでから push し直す（main に push すると Vercel に自動でデプロイされる）。
